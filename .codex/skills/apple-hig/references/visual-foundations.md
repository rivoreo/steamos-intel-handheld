# 視覺基礎（顏色 / 深色模式 / 版面 / 材質 / 動效 / 字體 / 圖示）

蒸餾自 HIG 的 `color`、`dark-mode`、`layout`、`materials`、`motion`、`typography`、
`icons`、`sf-symbols`、`images`、`app-icons`、`spatial-layout` 共 11 篇。這裡保留的
是**判準**——為什麼這樣設計、犯規時會壞在哪裡——不是像素表或匯出規格；watchOS /
tvOS / visionOS / CarPlay 的專屬細節與具體尺寸表已經砍掉。

## 1. 顏色：語意優先於美感

顏色的核心判準不是「好不好看」，是「語意有沒有守住」。同一個顏色不能同時代表
兩件事——如果用品牌色標示「這是可以點的」，又用相近色裝飾靜態文字，用戶會學不會
你的視覺語言，因為顏色本身不再攜帶穩定訊息。

**不要只靠顏色傳達狀態。** 色盲或低視力用戶無法單靠色相分辨差異，必須同時提供
第二個管道（形狀、文字標籤、圖示）。這不是無障礙的加分項，是「這個顏色語意能不能
成立」的前提——把顏色拿掉之後，訊息如果就消失了，說明這個設計從一開始就不完整。

對比是分層工具，不是裝飾。系統用 primary / secondary / tertiary 三階背景色表達
層級，靠的是亮度與透明度的階梯，不是靠多種色相堆疊。同一色系裡拉開亮度差，比换
成不同顏色更容易讓人讀出「這個包在那個裡面」。

文化語境會改變顏色的意涵（紅色在有些文化是危險，在有些文化是吉慶），選色不能只
考慮設計系統內部一致，還要考慮受眾怎麼解讀。

LunaTalk 落地：`DESIGN.md` §2.1 已經把顏色收斂成 token 表，一個畫面最多 2 個
accent——這正是「顏色語意不能被稀釋」判準的具體化，不要為了某個局部好看而額外加
色號打破這個收斂。

## 2. 深色模式：不是反色，是重新分層

最常見的錯誤心智模型是「把顏色數值反過來」。Apple 明確指出多數顏色不是簡單反轉：
深色模式下的背景色階（base / elevated）和文字色階都是**重新設計的獨立值**，不是
一套色被程式自動翻轉出來的。custom color 至少要各自準備亮／暗兩份，不能只做一份
再指望系統幫你翻轉。

**為什麼純黑不好：** 純黑背景會讓深色文字、深色卡片在視覺上「消失」在背景裡，而且
對比計算在極端值上反而更脆弱——要製造出可辨識的層次，需要更大的跳躍才行。用帶
色階的深灰（不是 `#000`）才留得出往下分層的空間，這正是 `DESIGN.md` §2.1「Dark
主題絕不用純黑」的判準來源。

深色模式的層次靠「提亮前景層」而不是「加深背景層」：一個 modal 或 sheet 疊在另一層
上面時，前景元素用更亮的背景色讓自己「浮起來」，而不是靠陰影變深——這跟淺色模式
常見的「加陰影表深度」思路是反過來的。

對比門檻是可測的驗收線，不是憑感覺：一般前景／背景對比不低於 4.5:1，自訂配色、小
字或需要更高辨識度的場景要拉到 7:1。

不要做「App 內深色開關」。除了讓用戶多一個要跟系統對齊的設定要調，還會讓他們誤以
為 App 沒有正確跟隨系統設定、覺得東西壞了。唯一的例外是刻意的產品決策（例如沉浸
式媒體閱讀器永遠只用暗色，是為了讓 UI 退到背景、聚焦內容），這種情況要能講清楚
「為什麼」，不能是圖省事。

## 3. 版面：層次靠順序、間距、對比，不是靠邊框

分組的目的是幫用戶找到想要的資訊，手法可以是留白、背景形狀、顏色、材質、分隔線
——但重點永遠是「內容跟控制項要保持清楚可辨」，不是分組手法本身有多花俏。

順序即層級：閱讀習慣是由上到下、由行首到行尾（注意 RTL 語言方向相反），所以最重
要的東西該放在最先被看到的位置，而不是用更大字級或更鮮豔顏色硬撐出重要感。

漸進揭露（progressive disclosure）：不要把所有功能攤平在一屏，用戶一次只需要看到
跟當前任務相關的東西；次要功能收進二級入口，用局部可見或滾動提示暗示「還有更多」，
而不是全部平鋪。`DESIGN.md` §1.5「功能分層」是這條判準的落地版本。

安全區不是留白美學，是硬需求：控制項必須避開裝置與系統的干擾特徵，而可滾動內容
應該能延伸到邊緣，不能被寫死的容器 padding 卡住捲動視窗的範圍——這正是
`DESIGN.md` §3.1「不要在 wrapper 上加 padding-top/bottom，改用 inner spacer」的
原因：padding 鎖死視窗，spacer 讓內容真的能滑到浮層背後。

適應性測試不是可選項：必須在最大、最小兩端佈局都測過，而不是只測「設計稿那個尺
寸」。五語言文案長度差異、字級放大後的擠壓，都屬於這一類必須驗證、而不是憑印象
判斷的變化。

## 4. 材質與深度：半透明是分層工具，不是裝飾

材質（通透、毛玻璃、厚薄）存在的作用是讓前景控制項跟背景內容「看起來在不同平
面」，藉此建立視覺層級，不是拿來當視覺花樣用。

判準：控制／導航層用玻璃材質，內容層不要用。把玻璃疊進內容層（卡片疊卡片都用玻
璃）會製造「哪個才是可以點的」的混淆——這正是玻璃系統把玻璃限定在浮層容器
（header / composer / sheet / drawer / popover）的原因。

什麼時候不該疊：當底層內容本身已經很豐富（照片、影片）時，疊加的玻璃層要嘛靠一
層額外的深色遮罩保證文字可讀，要嘛乾脆選更透明的材質讓底層內容說話——但兩個高
複雜度的視覺層絕不要同時堆疊（玻璃疊玻璃、材質疊豐富背景），疊多層的結果是誰都
看不清楚。

厚材質（更不透明）適合文字密集的場景，用來保證清晰度；薄材質（更透明）適合需要
讓用戶保留背景情境感的場景。這是一個「清晰度 vs 情境感」的權衡光譜，不是固定選
哪一種，要看該元件裝載的資訊密度決定。

## 5. 動效：要有目的、可中斷、尊重減少動態

**本節是上游依據。LunaTalk 落地取捨一律以 `DESIGN.md` §2.6（全 repo 只用 3 個
duration + 2 個 easing）為準；下方 Apple 的具體判準只用來理解「為什麼要克制動
效」，衝突時不要照搬 Apple 的做法，DESIGN.md 贏。**

動效存在的理由必須是「支撐體驗」，不是「讓介面看起來有生氣」。沒有目的的動畫只
會讓人分心、甚至造成生理不適——這條判準比任何具體的 duration、easing 數字都更
上位。

動效要匹配用戶的手勢期待：如果用戶用「往下滑」打開一個視圖，他不會期待「往側邊
滑」能關掉它——動作方向要跟手勢語意一致，不能只挑曲線好不好看。

精簡優先於炫技：簡短精確的回饋動畫通常比長動畫傳達得更清楚，也更不打斷任務節奏。

頻繁互動不需要額外動效：標準元件已經內建了細微動畫，自訂元件如果每次互動都要
「等動畫播完才能繼續」，等於在懲罰高頻操作的用戶。

可中斷是硬要求：不要讓用戶被迫等一個動畫播完才能做下一步操作，尤其是那個動畫他
這輩子要看很多次的情況（比如每次開合抽屜）。

尊重減少動態偏好：動效永遠不能是傳達關鍵資訊的唯一管道，視覺回饋要有其他管道
（文字狀態、觸覺回饋）並存，這樣關掉或降低動態效果的用戶不會漏掉資訊。

## 6. 字體：層級由字重＋字級＋行高共同構成

字級只是三個變量之一，字重和行距同樣決定「這段字看起來有多重要」。只靠放大字級
做層級，會導致字級變大了但字重雷同、層級依然模糊的結果。

避免用細字重（Light / Thin / Ultralight），尤其是小字——這些字重在小尺寸下辨識
度差；細字重帶來的「優雅感」只有在大字級時才成立，套在正文小字上是犧牲可讀性換
一點裝飾感。

一個介面裡的字體家族數量要收斂，混太多 typeface 會削弱層級而不是加強層級，還會
讓介面顯得內部不一致、缺乏設計意圖。

**尊重 Dynamic Type／用戶字級設定不是加分項，是前提。** 文字必須能跟著用戶選的
字級縮放，而且不是所有文字都要等比放大——次要或裝飾性文字（例如 tab 標題）可以
刻意不放大，把稀缺的視覺空間留給用戶真正關心的內容。

字級放大後最常見的破版來源是「截斷」：盡量避免在可滾動區域截斷文字，寧可讓文案
換行，也不要讓看不到的文字消失且用戶無法補救（例如另開一個視圖看完整內容）。

圖示要跟著文字字級一起放大：如果圖示承載著訊息卻在字級調大後維持原尺寸，會讓它
和旁邊文字的視覺比例失衡，甚至讓圖示相對變得更難辨識。

## 7. 圖示：一致的視覺重量，不用神秘圖示取代文字標籤

圖示的判準是「能不能被快速、普遍地認出」，不是「夠不夠有設計感」。過度精緻、細
節太多的圖示在小尺寸下會糊掉、看不清楚，等於失去了圖示存在的意義。

一致性是跨圖示的硬要求：同一個 App 內所有圖示要共用一致的尺寸、細節程度、線條
粗細、透視角度——即使自製圖示和系統圖示混用，也要對齊這四個維度，不然介面會顯
得像拼裝出來的。

圖示的字重要匹配旁邊文字的字重，除非刻意想讓其中一個更突出。

**神秘圖示是反模式。** 不要用一個用戶看不懂的圖示取代清楚的文字標籤，尤其是罕見
動作或非標準隱喻——寧可搭配文字，或者乾脆直接用文字，也不要指望用戶「猜對」圖
示含義。這條在冷門功能、次級操作（例如長按選單裡的稀有動作）上尤其容易被忽略。

每個自製圖示都要有替代文字（accessibility 描述），否則螢幕閱讀器用戶完全拿不到
這個資訊——這不是「最好有」，是圖示本身資訊完整性的一部分，缺了它等於這個圖示
對一部分用戶根本不存在。

SF Symbols 的分層渲染（hierarchical、多色）提供的是「表達深度和狀態變化」的手
段；但變動色（variable color）這個機制的語意是「傳達數值隨時間變化」（例如訊號
強弱、進度），不是用來表達深度層次——兩種機制承載的語意不同，不要混用錯位置。

## 8. 圖片與 App Icon：簡潔優先，不做 UI 截圖式圖示

（這兩篇原文以像素尺寸表、色彩空間、匯出流程為主，對我們可轉譯的判準集中在「設
計取捨」而不是規格數字，下面只保留判準。）

App Icon 的核心判準跟介面圖示一樣是「簡化到一個核心概念」，不要試圖把整個 App
的功能塞進一張圖裡——圖示的任務是讓人在一堆圖示裡快速認出你，不是介紹你的功能
清單。

不要在圖示裡放 App 截圖或直接複製 UI 元件的樣子。圖示需要在極小尺寸下依然可辨
識，UI 截圖包含的細節在那個尺寸下只會變成噪點，反而降低辨識度。

文字只在真正必要時才放進圖示，而且要能本地化。寫死的英文單字（如「New」
「Play」）在圖示裡既不能被翻譯，也常常是多餘資訊——App 名字本來就顯示在圖示
旁邊。

不要拿真實硬體外觀（自家或第三方）做圖示元素。硬體設計會迭代，圖示裡的硬體外觀
會很快顯得過時、拖累圖示的長期可用性。

圖片的通用判準：向量優先於點陣（可無損縮放，不需要為每個顯示密度另外準備一份資
產）；點陣圖必須為裝置像素密度提供對應倍率的版本，而不是指望系統幫你插值放大。
