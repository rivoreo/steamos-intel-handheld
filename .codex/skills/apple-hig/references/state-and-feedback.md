# 狀態與回饋（State & Feedback）

來源領域：alert／loading／progress／modal 呈現（sheet／popover／action sheet）／通知／
持續任務的環境化呈現。核心問題只有一個：**用戶需要知道一件事，你打算用多重的方式告訴他？**
選錯呈現方式，不是「不夠精緻」的問題，而是「傳遞方式跟資訊份量不匹配」的問題——太輕會被
忽略，太重會被討厭。

## 1. 核心判準：傳遞方式要匹配資訊份量

回饋在做四件不同的事，每一件都該用不同的「打擾程度」交付：

| 類型 | 在回答什麼 | 該有的形態 | 不該有的形態 |
|---|---|---|---|
| **狀態（status）** | 現在是什麼情況 | 嵌入介面裡的被動訊息（未讀數、進度條、小 icon）——用戶想看才看 | 跳出來打斷、要求用戶處理才能繼續 |
| **完成（completion）** | 一件重要任務成功了 | 只在「後果重大、用戶原本會擔心結果」時才給確認（例如付款成功）；一般操作預設成功、不用特地告知 | 每個小動作都跳確認，稀釋掉真正重要的那次 |
| **警告（warning）** | 這個動作有不可預期、不可逆的風險 | 打斷式（alert），並給明確的取消路徑 | 對「用戶本來就打算刪除/丟棄」的常規操作跳警告——那是預期內結果，不是意外 |
| **錯誤（error）** | 命令做不到，而且要讓用戶懂為什麼 | 具體說明卡在哪、可能怎麼辦 | 只說「發生錯誤」、給一個沒有資訊量的標題和「OK」按鈕 |

判斷順序：先問「這件事重不重要到需要打斷用戶」，重要才問「要不要用最重的 modal（alert）」。
多數回饋案例的病灶都是**分類分错**——把 status 級的資訊用 alert 級的方式硬塞給用戶。

## 2. 什麼時候該打斷，什麼時候不該

**不該打斷（改用被動呈現）：**
- 純資訊性、不需要用戶採取行動的內容——「用戶不會感謝一個只是提供資訊、但沒有動作可做的
  alert 打斷」。有資訊要給，就想辦法嵌進當下的畫面脈絡裡（例如一個可點的小提示、一個角標），
  而不是跳窗。
- 常見、可復原的破壞性操作（刪一封信、刪一個檔）——用戶執行這個動作本來就是為了丟棄它，
  警告只會變成一直被無視的雜訊。可復原（有 undo）進一步降低了警告的必要性。
- App 剛啟動的當下——這時候打 alert，用戶連介面都還沒摸熟就先被攔。有重要資訊要傳達，
  用「讓它容易被發現」取代「立刻打斷」；偵測到問題（例如沒網路）優先用快取/佔位資料
  + 不顯眼的狀態說明，而不是開場先跳窗。

**該打斷（值得用 modal / alert 級呈現）：**
- 用戶「沒有主動選這個後果」、但即將發生不可預期、不可逆的資料流失。
- 需要用戶明確確認或提供資訊，才能完成一個關鍵動作（例如需要密碼才能繼續）。
- 命令完全做不到，且原因對用戶決定下一步有幫助（見下方「錯誤要說清楚」）。

**Alert 要精簡使用**的深層原因：alert 每次出現都在消耗用戶的注意力信用。用得越隨便，用戶
就越傾向直接反射性關掉它——等到真正重要的那次出現時，它已經失去被認真對待的資格。

## 3. Alert 文案與按鈕：資訊量與可操作性缺一不可

- **標題必須傳達實際資訊**：說清楚發生了什麼、在什麼情境下發生、為什麼。「Error」或
  「發生錯誤 329347」這種標題等於沒講——用戶得不到任何能拿去做決定的線索。標題盡量一行
  講完，避免用戶還要展開閱讀。
  - 這條同樣適用於 LunaTalk 對用戶的錯誤訊息設計：症狀 + 情境比一個技術代碼有價值得多。
- **按鈕文字要描述「選了會發生什麼」**，用動詞或動詞短語（例如「清除」「轉換」「刪除」），
  不要用「OK」——OK 語意含糊，用戶分不清楚「OK＝我要繼續」還是「OK＝我知道後果了」。
  只有純資訊型、沒有選擇後果的 alert 才適合用 OK。
- 破壞性按鈕只在「用戶沒有主動選擇這個後果」時才需要強調樣式（destructive style）；
  如果用戶本來就是刻意執行這個破壞性動作（例如清空垃圾桶），按鈕不需要額外標紅——那是
  他原本的意圖，過度強調反而多餘。
- 有破壞性選項時一定要給 Cancel，且 Cancel 不該是預設按鈕（避免用戶按 Enter/Return 誤觸確認）。
- 不需要另外解釋按鈕在做什麼——如果標題和按鈕文字夠清楚，多加一段說明反而累贅。

## 4. Modal 呈現方式怎麼選

打斷用戶前，先確認「打斷到什麼程度」跟「任務複雜度」匹配：

- **Alert**：傳遞問題、警告或需要確認的關鍵動作。只有標題/簡短說明/最多三顆按鈕，不承載
  額外選擇。
- **Action sheet**：用戶剛做了一個**主動、有意圖的動作**、但這個動作衍生出幾個相關選項時用
  （例如取消編輯中的訊息，要問「刪除草稿／存草稿／回去繼續編輯」）。跟 alert 的差異：
  alert 通常是「意料之外」的事件通知，action sheet 是「你剛做的這件事，要不要細分一下」。
  選項別超過視窗可視範圍，能不捲動就不要讓它捲動。
- **Sheet**：需要用戶提供資訊或完成一個範圍明確的小任務，完成後回到原本畫面。按鈕語意要
  清楚分工：Cancel／Close 放棄不存、Done 完成並保存、Back 回上一步（不是用來關閉整個
  sheet）。三顆一起出現（Cancel + Done + Back）通常代表任務切分沒設計好，避免。
  只提供 Done 而不給退出路徑，會讓用戶覺得「完成任務是離開這裡的唯一方法」，觀感壓迫。
- **Popover**：只暴露一小撮資訊或幾個相關操作，用完即關。位置要盡量指向觸發它的元素，
  避免蓋住觸發源或用戶正在看的內容。一次只開一個，不要讓 popover 疊 popover。popover
  不適合拿來承載警告——用戶很容易漏看或誤觸關閉，警告要用 alert。
- **一次只給一個 modal**：多個 modal 疊加會讓用戶忘記自己原本在哪個情境，唯一的例外是
  alert 可以蓋在任何 modal 之上（因為它本身就代表最高優先級的打斷）。
- 關閉 modal 若會造成用戶生成內容遺失，關閉前一定要能確認或補救（例如提供存檔選項），
  不要讓「一個手滑的關閉動作」變成不可逆的資料流失。

## 5. 等待與載入：不確定感比等待本身更難受

- **盡快先讓畫面上出現東西**。空白畫面會被解讀成「壞了」，不是「還在跑」。用佔位文字/
  骨架/動畫先撐住畫面，等內容備妥再替換掉，而不是等一切就緒才一次性顯示。
- **能背景載入就別鎖死互動**。讓用戶可以在等待期間做別的事，比讓他們乾等體感好很多。
- **確定型（determinate）優先於不確定型（indeterminate）**：只要能算出還要多久，就顯示
  精確進度——這能幫用戶決定「要不要先去做別的事、要不要現在放棄」。做不到才退回不確定型
  的轉圈動畫（它只能證明「還活著」，不能幫用戶做決策）。
- 確定型進度要**盡量準確、步調均勻**。前 90% 五秒衝完、剩下 10% 卡五分鐘，會讓用戶覺得
  卡住了、甚至覺得被騙。
- 進度指示器要**持續動**，靜止的指示器會被當成當機或卡死的信號；如果真的卡住了，要主動
  說明卡在哪、用戶能做什麼，而不是讓它繼續空轉裝忙。
- 長時間等待且無法避免時，與其讓用戶盯著轉圈，不如給點有內容的東西看（操作提示、功能
  介紹），但要對等待時間有合理估計，別讓內容太快看完或太長重複播放。
- 可以中斷的流程就給 Cancel；中斷會有副作用（例如已下載的部分作廢）就額外給 Pause，並且
  「取消會造成的損失」要讓用戶在取消前就知道，不要事後才發現。

## 6. 「做不到」要說清楚，而且要說為什麼

用戶送出一個指令、系統辦不到時，不能安靜失敗或只丟一個空泛錯誤。要讓用戶知道：
（1）沒成功；（2）卡在哪個環節或前提缺什麼；（3）如果可能，接下來能怎麼調整再試。
這條原則同時解釋了「錯誤 alert 標題不能只寫 Error」與「進度卡住時要主動說明」——本質上
是同一件事：**系統知道出了什麼問題時，沒有理由不告訴用戶**。

## 7. 通知：稀缺資源，不能濫發

通知動用的是用戶裝置最貴的注意力入口（螢幕亮起、聲音），節制原則比呈現細節更重要：

- 送通知前必須先取得同意；用戶也隨時能在系統設定調整或關閉——把這當成一個**要靠內容品質
  持續贏得的權限**，不是拿到就能濫用的管道。
- **同一件事不要重複發**，即使用戶還沒回應。塞爆通知中心只會讓用戶乾脆整批關掉這個 App
  的通知——這是不可逆的信任損耗。
- 通知內容要簡潔、能一眼看懂在說什麼；避免只給指令式的「請回到 App 做某件事」而不給
  上下文——用戶事後根本記不住要做什麼。
- App 在前景時不要跳通知，改用「不打斷但看得到」的方式呈現（角標、把新資料悄悄插進當前
  畫面），因為此刻用戶的注意力已經在你的介面上，跳通知只是多餘的打斷。
- 通知不是拿來裝錯誤訊息的地方——錯誤要用 alert 這種明確、可互動的呈現，通知的角色是
  「稍後可查看的簡訊」，不是「現在必須處理的警報」。
- 誠實標示急迫程度（不要什麼都標成最高優先），過度誇大急迫度換來的短期關注，long-term
  會讓用戶對這個 App 的所有通知都降低信任、乾脆整批靜音。
- 行銷/推廣類通知要走**額外、明確的同意**，而且無論如何都不能用最高急迫層級發送——
  用戶就算同意收行銷內容，也沒有同意被最高優先級的方式打斷。
- 避免放入任何敏感、私人或機密資訊——通知可能在用戶不在你可控情境下的螢幕上被別人看到。

## 8. 持續進行中任務的環境化呈現（可遷移原則）

Apple 的 Live Activity（動態島／鎖屏常駐卡）是平台特化功能，但背後的判準可以遷移到任何
「有始有終、進行中需要被看見」的任務型 UI（例如：批次匯出、長時間生成、排隊中的操作）：

- 只在任務**有明確開始與結束**、且時長可預期的情境使用這種常駐呈現，別把它當成一般狀態展示。
- 只展示用戶此刻最需要的關鍵資訊，其餘留給用戶主動點進來查看的詳情頁——常駐位置寸土寸金，
  不要塞。
- **內容真的變化時才更新**，沒變化就維持原樣，避免製造「一直在跳動」的干擾感。
- 需要用戶注意的更新才用會發聲/亮屏的強提醒；同一個更新不要既跳強提醒又疊一則獨立通知，
  兩者是重複打擾。
- 任務結束要**立刻收掉**常駐呈現（或給一個跟任務時長成比例的短暫展示期），別讓已經結束的
  任務繼續佔用用戶的常駐視覺空間。
- 如果用戶同時在追蹤多個同類事件，優先用「一個容器輪替顯示」取代「開好幾個並存的常駐卡」，
  減少用戶需要在多處來回確認的負擔。

## 9. 檢查表

1. 這個回饋屬於狀態／完成／警告／錯誤哪一種？呈現方式跟它的份量對得上嗎？
2. 這則 alert 是不是純資訊、沒有任何動作可選？如果是，改成非打斷式呈現。
3. 這個破壞性操作是常見且可復原的嗎？如果是，不需要警告 alert。
4. Alert／錯誤標題有沒有具體資訊？是不是寫了「Error」這種等於沒講的話？
5. 按鈕文字是不是在描述「選了會發生什麼」？有沒有濫用「OK」？
6. 這次要用的是 alert、action sheet、sheet 還是 popover？有沒有選重了或選輕了？
7. 有沒有同時疊出兩個以上的 modal？
8. 載入時畫面是不是曾經空白過一瞬間？有沒有先給佔位內容？
9. 能不能用確定型進度取代不確定型轉圈？如果不能，是不是至少讓指示器持續在動？
10. 命令失敗時，用戶知不知道卡在哪、下一步能做什麼？
11. 這則通知是不是在重複發同一件事，或者在 App 前景時還跳出來打斷？
12. 常駐/持續任務的呈現，是不是在任務結束後還賴著沒收掉？
