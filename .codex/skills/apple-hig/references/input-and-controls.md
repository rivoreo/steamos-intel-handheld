# 輸入與控制項

蒸餾自 HIG 的按鈕、文字欄／文字檢視、選單、情境選單、選擇器、開關、滑桿、
步進器、分段控制、清單與表格、集合、捲動檢視、頁籤列、工具列、側邊欄、搜尋欄、
手勢、鍵盤、虛擬鍵盤、系統控制項共 20 篇。這份不是元件規格表，是「該用哪個
控制項、該怎麼分層、該怎麼讓人不迷路」的判準集合。挑元件本身不是重點，重點
是**每個控制項背後在替用戶做什麼決定，以及那個決定該花多少力氣**。

## 一、先問：這是「動作」「狀態」還是「選擇」

三種輸入语意常被混用，混用了介面就會說謊：

- **動作**（做一件事，做完就結束）→ 按鈕。
- **狀態**（在兩個對立值之間切換，且立即生效）→ 開關。開關永遠代表「現在
  就是這樣」，不是「按下去才生效」——如果需要先選好、按確認才生效，那其實
  是選擇，不是狀態，別用開關硬套。
- **選擇**（從一組選項中挑，可能離開當下畫面才能挑）→ 選單、選擇器、分段
  控制，依「選項多少、多久用一次、要不要保留脈絡」再分。

分段控制只在「選項彼此緊密相關、都跟同一個物件/檢視有關」時用，且一個控制
項裡只能單純做「選擇狀態」或單純做「觸發動作」二選一——不能一部分是切換
狀態、一部分是按鈕，那樣視覺一致但語意打架，用戶會分不出哪個segment 是
「已選取」哪個是「按下去會發生事」。分段數也要克制：選項一多，掃視和點按
都變慢，這時該換選單或清單。

滑桿適合「連續值、範圍大、精確度不重要」；步進器適合「離散值、小幅調整」。
兩者都不擅長「用戶想直接打一個具體數字」——如果數值範圍很寬，或用戶常常
知道自己要多少，搭一個文字欄位比逼人拖到準沒有效率。步進器本身不顯示數值，
所以永遠要跟一個顯示當前值的欄位放在一起，否則用戶按了但看不到在改什麼。

## 二、主次動作的層級：一屏最多一兩個「重的」選擇

視覺份量本身就是一種語言。一屏裡把最可能被選的動作標成醒目樣式，其餘動作
用普通樣式——**用樣式分層，不要用尺寸分層**。兩個大小不同的按鈕擺在一起會讓
介面顯得雜亂不協調；反過來，如果兩個按鈕代表一組並列選項（不分主次），它們
就該同尺寸同樣式，尺寸一致本身在告訴用戶「這是一組」。

醒目樣式（例如佔滿強調色的按鈕）每屏最多用一到兩個。用醒目樣式喊出太多
「這個很重要」，等於什麼都不重要——用戶得花更多認知力氣才能決定要選哪個，
違背了醒目樣式原本要省掉的那步判斷。

主要動作（primary，通常是 Return 鍵預設觸發、且能讓臨時性畫面自動關閉的那個）
永遠只能給「非破壞性」的選擇。破壞性動作即使是用戶最可能選的那個，也不能
套主要動作的視覺重量——因為視覺醒目本身會誘使人不看清楚內容就點下去。破壞
性動作的正確待遇是**降權**：用比較不顯眼的樣式，必要時用警示色（不是主色）
標出「這會造成資料損失」，而不是用醒目色把它捧成首選。

## 三、能選就別讓人打字

文字輸入是介面裡成本最高的互動之一——要叫出鍵盤、要打字、常常要跨語言驗證、
在小螢幕或手持裝置上更慢更容易出錯。輸入類元件的決策順序應該反過來想：
**先問「能不能讓他選，而不是讓他打」**。

- 如果合法值就是一組固定選項（日期、時間、國家、單位），用選擇器而不是
  文字欄——選擇器不需要驗證格式，也不會出現用戶自己都不確定該怎麼打的
  情況。
- 如果要收集的是一小段自由文字（姓名、Email），用文字欄，並用提示文字
  （placeholder）告訴用戶這格要填什麼；提示文字會在開始打字後消失，所以
  重要脈絡最好再配一個常駐標籤，不要只靠提示文字撐著。
- 如果是長篇、可能需要格式化的內容，用文字檢視（text view），不要硬塞進
  文字欄。
- 敏感資料（密碼）一定要用遮蔽輸入，這不是可選項。
- 數字輸入盡量用專用的數字格式化與鍵盤類型，讓輸入法本身先擋掉非法字元，
  而不是等用戶打完錯的再驗證報錯——能在輸入當下就防呆，就不要等送出才罰。
- 手持裝置、或任何「移動中/短暫互動」場景，**能不打字就不打字**。這條在
  可穿戴裝置上是鐵律，但邏輯對任何小螢幕或單手操作場景都成立：能用按鈕、
  清單、選擇器解決的，就不要逼人叫出鍵盤。

驗證的時機要配合欄位語意：對錯很明確、跟其他欄位無關的（例如「這格只能是
數字」），可以即時擋；需要跨欄位判斷或需要用戶明確確認完才有意義的（例如
Email 格式、密碼強度），等切換到下一欄位再驗證，不要在他還沒打完就急著報錯。

## 四、按鈕、選單項的文案：說結果，不說操作

按鈕與選單項的標籤要讓用戶「不用試就知道按下去會發生什麼」：

- 用**動詞或動詞片語描述會發生的結果**，而不是描述元件本身。「加入購物車」
  比「確定」清楚；「刪除角色」比「是」清楚——後者逼用戶回頭讀上面那句才
  知道自己在同意什麼。
- 圖示搭配動作要用大家已經有共識的視覺語彙（例如分享圖示），不要為了風格
  統一硬造一個用戶要重新學習的符號。
- 一個動作如果按下去**不會立刻完成**，而是要先跳出另一個畫面收集更多資訊
  （例如要再選一次、再填一個表單），標籤結尾加一個省略符號，提前告訴用戶
  「這不會馬上做完，還有一步」。省略符號本身就是一種期望管理，省了它，
  用戶會誤以為按下去就結束，結果卻被丟進另一個畫面，感覺被騙。
- 選單裡表示開關狀態的項目，標籤本身最好隨狀態變化描述「按下去會變成什麼」
  （例如從「顯示地圖」變成「隱藏地圖」），而不是靜態描述「現在是什麼」；
  如果單靠變化的標籤還是看不出這是動作還是狀態說明，就把動詞加回去講清楚。

## 五、不可用：要真的不可用，不是只有灰階樣式

「用戶還沒提供必要資料，這個動作暫時不能做」時，對應的控制項必須**真正**
擋下互動，不只是視覺上變淡。這不是美觀問題，是承諾問題：一個看起來灰但其實
點了會發生奇怪反應（或什麼都不發生但沒有解釋）的按鈕，比明確擋下更糟——用戶
會以為介面壞了，或者以為自己操作有誤，開始亂點別的地方找出路。

同樣的邏輯反過來也成立：如果一整組選項當中「有些暫時不可選」，通常該讓那個
容器本身保持可開啟、可瀏覽（讓用戶能看見完整選項並理解「為什麼這項現在不能
選」），只讓個別項目失能，而不是把整個入口也一起藏起來或關閉——「找不到功能」
和「功能暫時關閉」給用戶的訊息完全不同，後者至少讓人知道系統沒壞，只是時機
不對。

按鈕本身也永遠需要一個明確的按壓/點擊回饋狀態。沒有回饋，用戶按下去那一刻
無法確認系統收到了輸入，最常見的後果就是重複點擊——對任何會產生副作用（下單、
送出、扣款）的動作而言，這種重複點擊等於让用戶自己造成了原本不該發生的重複
執行。

觸控／點擊熱區要比視覺元素本身大一圈，讓周圍留白足夠、跟旁邊元素有清楚的
間距。熱區太緊會造成兩種對稱的傷害：手指按不準而多次嘗試，或者按到了鄰近
的、原本沒打算選的項目——兩者對用戶而言都是「這介面不聽話」。

## 六、清單與大量資料：怎麼避免讓人迷路

清單/表格是呈現大量文字內容最直接的形式，但資料一多，用戶最容易迷失的
不是「找不到項目」而是「不知道自己現在在看的是全部的哪一部分」。幾條共通
原則：

- 條目文字保持精簡。內容太長會被截斷或換行，兩者都傷害可掃視性；如果每項
  本身內容量就很大，寧可清單只列標題、選中後才在詳情畫面展開全文，也不要
  硬把整段塞進一行。
- 選中一個項目後的回饋要分兩種情境處理：如果選擇會**帶你前進到下一層**
  （導航型清單），選中狀態要持續高亮，讓用戶清楚自己走到哪一步、還能不能
  退回去；如果選擇只是**切換某個選項的狀態**（例如打勾），高亮應該是短暫的，
  用一個明確的標記（如勾選符號）取代，而不是讓整行一直亮著造成「這是導航」
  的錯覺。
- 多欄位表格如果允許排序，欄位標題本身就該是可點擊的排序入口，且再點一次
  要能反轉排序方向——這是用戶對「可排序表頭」已有的既定期望，換一套互動
  方式只會增加學習成本。
- 集合（以圖像為主、非文字為主的網格/橫列呈現）跟清單/表格該按內容類型
  二選一，不要混著判斷：文字為主的內容用清單效率更高、更好掃視；圖像為主
  的內容用集合的網格/橫列呈現更直覺。硬把大量文字塞進圖像集合的卡片裡，
  會犧牲兩邊的優點。
- 捲動本身要讓用戶感覺得到「還有更多內容」。捲動指示器不一定隨時可見，所以
  版面設計上最好讓即將捲出畫面的內容露出一點邊緣，暗示「這個方向還有東西」，
  不要讓一屏看起來剛好裝滿、實則後面還有一大截。
- 不要把兩個捲動方向相同的捲動容器互相嵌套——這會讓手勢意圖變得模糊不清，
  使用者拖動時不知道在滾動外層還是內層。水平捲動嵌在垂直捲動裡（或反過來）
  沒問題，因為手勢方向本身就消除了歧義。
- 搜尋是清單/大量資料的逃生門，不是附加功能。可以做的話盡量做到「邊打字邊
  出結果」而不是要等按下確認鍵，這會讓搜尋的回應感明顯提升；結果本身要把
  最相關的排在最前面，必要時再用範圍篩選（scope）把大範圍逐步收斂到小範圍，
  而不是一開始就把範圍鎖死——用戶通常需要先看到全貌，才知道要怎麼縮小。

## 七、導航骨架的選擇：頁籤、側邊欄、分層推進

三種常見骨架各自解決不同規模的問題，選錯骨架的癥狀通常是「功能都在，但
用戶老是找不到」：

- **頁籤列**：適合「App 有少數幾個地位相當、用戶會頻繁切換」的大分區，
  且頁籤本身用來做導航，不是用來做動作——如果某個按鈕的作用是「對當前畫面
  的內容做一件事」而不是「切去另一個分區」，那不該塞進頁籤列，該用工具列。
  頁籤列一旦顯示就不該在同一分區內消失或被停用；分區暫時沒內容，用畫面內的
  空狀態解釋原因，而不是把整個頁籤藏起來或灰掉——藏起來或灰掉會讓整個導航
  結構顯得不穩定、不可預期，用戶會開始懷疑其他頁籤是不是也會突然消失。
- **側邊欄**：適合「資訊架構比頁籤列能撐的更深，且用戶願意花更多螢幕空間
  換取更完整的導航總覽」的場景，通常需要較寬的版面。側邊欄裡的階層盡量
  收在兩層以內；超過兩層寧可讓側邊欄只負責第一層分類，第二層資料改用清單
  或分割檢視承接，不要在側邊欄裡疊套更多層——側邊欄一旦要展開三層以上的
  樹狀結構，用戶掃視和記憶的負擔會迅速超過它原本要節省的那點導航成本。
- **分層推進**（例如清單點進去、詳情頁再點進去）：適合「資訊本身就有明確
  父子關係、用戶一次只需要專注在一層」的場景，用戶靠回上一層的動作找路。
  這個模式最怕「進去了卻不知道怎麼退」——回上一層的入口必須隨時可見、行為
  一致，不能因為畫面不同就換了退出方式。

三者不是互斥選項，很多產品讓頁籤列可以收合成側邊欄，或在側邊欄裡的某個
分類下再用分層推進——重點是同一個 App 裡「切換分區」永遠用同一種手感，
不要有的分區用頁籤有的分區用抽屜又有的用側滑，那會逼用戶為每個分區重新
學一次操作方式。

工具列跟頁籤列的分工要分清楚：**工具列作用在「當前畫面的內容」上**（返回、
編輯、分享、搜尋這類動作），**頁籤列作用在「App 的分區」上**。把兩者的
職責對調——例如用頁籤代表動作，或用工具列做跨分區導航——是最常見的骨架
錯誤，會讓用戶對「按這個會不會離開現在畫面」失去預期。工具列上的項目數量
也要克制，塞太滿會犧牲每個項目的可辨識度；真正次要的動作收進「更多」，
但常用動作要盡量都留在工具列本身，只有真的必要才建第二層。

## 八、手勢：什麼能自訂、什麼絕對不能覆寫

手勢的判準比其他控制項更嚴格，因為手勢是「隱形契約」——用戶不是讀說明學會
的，是靠系統一致性的肌肉記憶學會的。破壞這個一致性的成本遠高於其他 UI 元素。

- **標準手勢（點按、滑動、拖曳等）的意涵在任何情境下都該一致**。不要拿一個
  大家已經有固定期望的手勢去做一件不相關的事（例如把「滑動」拿去觸發跟捲動
  無關的隱藏動作），也不要為「啟動按鈕」「捲動長清單」這種本來就有標準手勢
  的操作另外發明一套手勢——那既增加學習成本，也會跟系統手勢搶輸入。
- **自訂手勢只在「高頻率、專屬於這個功能、且沒有既有手勢覆蓋」時才值得加**，
  典型場景是繪圖、遊戲這類需要精細直接操作的體驗。加了就要讓它容易被發現、
  容易學會、跟其他手勢動作明顯不同，而且**永遠不能是完成一個重要動作的唯一
  路徑**——一定要留一條用按鈕或選單也能走到底的路，因為不是每個人都能做出
  或發現那個自訂手勢。
- **系統保留給平台層級操作的手勢，任何情況都不能覆寫或搶奪**。這些手勢
  用戶已經預期它們在所有 App 裡行為一致（叫出系統選單、切換 App 這類），
  自訂手勢設計時要主動避開和它們衝突的動作路徑，寧可选一個系統沒用到的
  手勢，也不要跟系統手勢搶輸入焦點。
- 對用鍵盤操作的用戶，系統定義的標準快捷鍵不要挪用去做不相關的事——人已經
  對這些組合鍵有肌肉記憶，行為對不上會直接產生「這東西壞了」的觀感。真的
  需要自訂快捷鍵，只保留給用戶會高頻使用、且沒有標準快捷鍵覆蓋的動作，並且
  一律優先支援「純鍵盤也能完整操作全部功能」這條路徑，不要讓鍵盤使用者被迫
  在某個環節切回滑鼠或觸控。
- 手勢或按鈕在特定狀態下不可用時，要把「不可用」跟「可用」做出清楚的視覺
  或行為差異。什麼都不解釋地讓一個動作沒有反應，用戶多半會以為是自己操作
  失誤，而不是理解成「這裡本來就不能這樣做」，於是反覆重試、越試越挫折。

## 檢查表

送出設計或 review 輸入/控制項相關改動前，逐條確認：

1. 這個控制項的語意是「動作」「狀態」還是「選擇」？三者有沒有混用在同一個
   元件裡？
2. 這一屏的醒目樣式是不是只給了一兩個最可能被選的動作，其餘動作有沒有明顯
   降權？
3. 破壞性動作有沒有被誤放進「主要/預設」位置？視覺上是不是刻意比首選動作
   更收斂？
4. 有沒有能靠「選」解決卻要求用戶「打字」的欄位？能不能換成選擇器/清單？
