# 控制與恢復（Control and Recovery）

一句話貫穿全篇：**用戶要感覺資料與動作是自己的，不是系統的。** 這包括能反悔（撤銷）、
能預判（輸入驗證）、能全身而退（刪帳號、取消訂閱要跟開通一樣容易），以及付費時不被
暗中牽著走。下面的判準圍繞這條軸線重新組織，不是照原始篇目順序排。

## 一、撤銷與重做：可逆優先於確認

**核心判準**：常見、可逆的動作不要用確認彈窗攔一次；把它做成「先做，但可以退回」，
比「先問你要不要做」更尊重用戶，也更不容易被無腦點過去。過度確認會訓練用戶閉眼按
下一步，真正該攔的時候反而攔不住。Apple 的編輯選單（剪下／貼上／格式化）刻意不要求
確認，理由就是「反正可以撤銷」——這是判斷「該確認還是該可撤銷」時最直接的參照。

**看不到結果會導致用戶重複執行，對計費型產品是實害。** 如果撤銷或重做影響的內容已經
捲出畫面外，必須主動把畫面捲回去讓用戶看到變化；用戶看不到任何反應時，會以為沒生效，
於是再按一次。如果那個動作背後綁著計費（AI 回覆、扣點、下單），這就是實打實地讓用戶
多付一次錢。同理，任何「按下去會改變狀態」的動作，當下都要有看得見的即時回應，不能
讓用戶靠猜的。

**不要限制撤銷次數。** 用戶預期能一路撤銷回到「打開文件」或「上次儲存」那個時間點，
硬性限制次數只會製造「早知道就不要點那麼快」的懊悔，也逼用戶對每一步操作過度小心。

**能一次撤銷一整批，就不要逼用戶按 N 次。** 一連串細碎但邏輯上屬於同一件事的調整
（例如連續微調同一個屬性），最好能整批一次撤銷，而不是要求逐一倒退回去。

**撤銷入口走系統慣例，不要自造手勢。** 需要專屬撤銷／重做按鈕時才放，且放在用戶預期
的位置（工具列）；操作方式一旦跟平台習慣不一樣，用戶連「這能不能撤銷」都會猜錯。

## 二、輸入：讓用戶少打字、少猜、少被騙

**能給選擇就不要讓人打字。** 只要能用清單、下拉、picker 表達的資訊，就不要開一個
自由輸入欄——打字比選擇容易出錯，也比較累，尤其在手機鍵盤上。

**不要問系統已經知道的事。** 定位、行事曆、裝置設定這類系統本來就能取得或授權取得
的資訊，不要再開一個欄位讓用戶手動填一次；那是在用用戶的時間換系統的懶惰。

**即時驗證，不要等提交才報錯。** 用戶填完一長串欄位、按下送出才被告知某一欄有問題，
是最容易累積挫折感的錯誤時機。應該在用戶離開欄位、或輸入到能判斷對錯的那一刻立刻給
回饋，讓他當下就能修正，而不是事後回頭逐一找。數字類輸入尤其適合用格式化規則（小數
位、百分比、貨幣）幫用戶把格式做對，而不是等他打錯再罵他。

**「需要資料才能繼續」時，按鈕要真的不可用。** 如果流程要求先填完必要欄位才能繼續，
那顆按鈕在條件不滿足時就該是真正的 disabled 狀態，而不是「看起來能按，按下去才跳
錯誤」——先讓用戶知道「還缺什麼」，比讓他按下去才被打回票更省他的力氣。

**盡量支援拖放與貼上，不要逼人重打一次。** 只要資料已經存在於某個地方（另一個欄位、
剪貼簿、拖曳來源），就該讓用戶把它搬過來，而不是要求重新輸入一遍。

**密碼欄位永遠不要預先填值**，一律要求用戶主動輸入或走生物辨識／金鑰驗證；這是安全
底線，不是體驗選項可以妥協的地方。

**搜尋也是一種輸入，一樣適用「給選擇不要逼打字」。** 顯示最近搜尋、輸入中即時給預測
建議，都是幫用戶少打字、少猜關鍵字。但搜尋紀錄涉及隱私，如果會被別人看到（例如共用
裝置），一定要給用戶自己清空紀錄的方法，不能預設永久保留。

## 三、破壞性動作：什麼該攔、什麼不該

**判準只有一條：這個動作事後能不能復原？**

- **能復原**（絕大多數編輯、刪除單一項目且提供撤銷、拖放搬移）→ 不需要確認彈窗，
  做完直接給撤銷入口就好，讓用戶事後反悔比事前猶豫更順暢。
- **不能復原、後果重大**（清空資料、刪帳號、扣款、不可逆的分享）→ 才值得用一次
  確認打斷用戶，而且要讓這次確認本身有意義，不是流於形式。

**確認彈窗的按鈕要講「會發生什麼」，不要只寫「確定／取消」。** 用動詞描述具體後果
（例如「刪除對話」而不是「確定」），讓用戶按下去之前就知道自己在同意什麼，而不是
盲目點掉一個擋路的彈窗——含糊的按鈕文字等於沒有確認。

**容易誤觸的動作，優先做成可撤銷，其次才考慮確認。** 以拖放為例：如果某個結果真的
無法撤銷（例如放進一個之後打不開的位置），才在放下那一刻攔一次確認；否則寧可讓它
先發生，事後給撤銷。放錯地方或放到不接受的目的地時，要有清楚的視覺回饋（退回原位、
或明確的「不允許」提示），不要讓用戶懷疑動作是不是真的失敗了、又忍不住重試一次。

**自動儲存優先於要求用戶手動存檔。** 用戶不該需要做一個額外動作才能「不丟掉工作」；
系統應該在編輯過程中與離開時自動保存，讓「資料會不見」這件事本身就不成立。如果產品
真的允許關掉自動儲存，就必須清楚標示「目前有未存的變更」，不要讓用戶帶著錯誤的安全感
離開現場。

## 四、帳號與資料歸屬：進得來，也要出得去

**開帳號前先讓人試用。** 逼人一開頭就註冊會讓人直接流失；能力所及先讓用戶感受到
價值，真正需要留存或消費時才要求登入，這也是留存率更高的路徑。

**能刪帳號，不能只能停用。** 提供建立帳號功能的產品，必須同等提供刪除帳號的路徑，
而不是只給「停用」搪塞；找到刪除入口的難度，不該高於找到註冊入口的難度。若刪除需要
時間，要讓用戶知道大概什麼時候完成，並在完成後主動通知——按了卻沒下文，跟沒做一樣。

**刪帳號不等於自動停止扣款。** 如果產品有訂閱或定期扣款，刪帳號後仍要清楚告訴用戶
訂閱本身要另外取消，否則他會誤以為砍了帳號等於砍了帳單，事後才發現繼續被扣款而感覺
被騙。

## 五、分享與協作：權限講清楚，選項給到剛好

**用一句話講清楚誰能做什麼。** 分享權限的文案要能一眼看懂範圍，例如「只有受邀者能
編輯」還是「所有人都能修改」，不要留給用戶自己猜測共享後的後果。

**權限選項數量收斂，不要每種排列組合都攤開。** 給「可看／可編輯」「能不能再邀請別
人」這種少量、彼此獨立的開關就夠；選項一多，用戶反而看不出自己正在同意什麼。

**協作中的變更要能被看見、被追溯。** 有其他人加入、離開、修改共享內容時，讓用戶知道
發生了什麼，而不是靠他自己比對前後版本才發現東西被誰動過——這也是「掌控自己資料」的
一部分，只是對象從單人操作擴大成多人共享狀態。

## 六、付費與訂閱：把帳算清楚，不要用機關擋人

**每一筆消費都要能看到總價，且是完整、正確、已本地化的總價。** 不管是單次購買還是
訂閱，用戶下決定前必須清楚知道總共要付多少錢，不能只給模糊的相對描述帶過。

**免費試用結束會自動扣款這件事要講白，不能靠沉默帶過。** 用戶必須明確知道試用什麼
時候結束、結束後會自動扣多少錢，而不是等扣款通知才發現自己「被訂閱了」。

**取消訂閱要跟訂閱一樣容易，絕不能刻意藏起來或繞路。** 如果取消入口埋得很深、或
流程故意拉長，用戶會感覺自己被刻意困住——這是暗黑模式，不是體驗設計上的疏忽。已經
訂閱的用戶也不該再被推促「訂閱」，那會讓人誤以為前一份訂閱已經失效了。

**永遠提供恢復購買／找回訂閱的路徑。** 用戶換裝置、重灌 App、或帳號狀態變動時，要
有明確的「恢復購買」入口，不要讓已經付過錢的人以為要再付一次才能拿回權益。

**退款或申訴流程不要製造阻力。** 提供求助資訊、常見問題可以，但不能拿這些內容擋在
「申請退款」按鈕前面，逼用戶多滾動、多點幾層才找得到真正想要的入口。

**先讓用戶感受到價值，才問他要不要付費。** 在用戶還沒體驗過核心功能前就跳出付費牆，
容易被當成一開頭就要錢，觀感遠比晚一點才問更差。

## 七、別在用戶專注的時候打斷他

以評分邀請為例：只在用戶完成一個有意義的任務、明顯有空檔時才詢問；不要在剛啟動、
還沒建立信任時就開口，也不要在他正忙著操作時打斷——被打斷的人更容易給負評，而不是
更願意配合。同樣的節制也適用於任何「非用戶主動觸發」的彈窗：問過一次、被拒絕或忽略
後，就不要短時間內反覆糾纏。

**焦點與選取不要無故被系統搬走。** 用戶靠畫面上「目前選到哪裡」認知自己的位置；如果
系統在用戶沒有動作的情況下自己改變焦點或選取狀態，等於逼他重新找路，浪費他原本要做
的事，也會讓他懷疑是不是自己的操作出了問題。

## 檢查表

- [ ] 這個動作能撤銷嗎？能的話有沒有做成撤銷而不是先問確認？
- [ ] 撤銷／重做的結果，用戶看得見嗎（尤其是影響到畫面外的內容時）？
- [ ] 有沒有限制撤銷次數？能不能拿掉？
- [ ] 必填資料能不能用選單／選擇取代自由輸入？
- [ ] 系統已經知道的資訊，有沒有又跑去問用戶一次？
- [ ] 輸入驗證是即時的，還是要等提交才報錯？
- [ ] 「資料不齊全不能繼續」的按鈕，是真的 disabled，還是按下去才報錯？
- [ ] 真正不可逆、後果重大的動作，確認按鈕有沒有講清楚會發生什麼（不是只有「確定」）？
- [ ] 刪帳號的入口，跟開帳號的入口一樣好找嗎？刪帳號有沒有清楚提醒訂閱要另外取消？
- [ ] 訂閱的總價、試用到期後扣款金額，有沒有在用戶付款前講清楚？
- [ ] 取消訂閱、恢復購買的入口，找得到、走得順嗎？
- [ ] 任何非用戶觸發的打斷（評分邀請、推廣彈窗），時機是不是挑在用戶的空檔？
