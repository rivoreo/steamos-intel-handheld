# 交付形態與平台判準

蒸餾自 HIG「Designing for iOS / iPadOS / macOS」「Launching」「Multitasking」「Windows」
「Status Bars」「Home Screen Quick Actions」「App Shortcuts」「Widgets」「Web Views」
「Mac Catalyst」。

LunaTalk 不寫原生 iOS/macOS App，這份文件的價值不在「怎麼寫 App」，而在**手機
H5、安裝成 PWA、原生 App 三種交付形態下，用戶帶著不同的預期進來，我們常常誤用
了其中一種預期去服務另一種形態**。判斷任何一個互動設計時，先問「用戶現在是用
哪一種形態在用我們」，再套對應的規則。

## 1. 觸控 vs 指標：兩套輸入假設不能共用一套 UI

手機是單手操作、視距不到一兩尺，畫面中下段是拇指最容易到達的區域——這是側滑
返回、composer、常用操作要放在畫面下半部的原因。桌面/滑鼠沒有這個限制，指標
精度高，人習慣從上到下掃視，所以工具列放在頂端反而合理。**同一組常用操作不要
不假思索地在兩端用同一種擺放邏輯**：手機上把主要 CTA 塞在頂部，等於逼用戶伸長
拇指去搆一個本來該在底部的按鈕。

**hover 在觸控裝置上不存在。** 任何靠 hover 才浮現的資訊（tooltip、預覽、次要
操作）在手機上永遠不會被看到。設計時要先確認：這則資訊有沒有觸控可達的等價路
徑（長按展開、點擊顯示），如果沒有，等於這則資訊在手機上直接消失。

**長按對應右鍵，但觸發時機不同。** 長按是計時手勢（LunaTalk 定 450ms，見
`DESIGN.md` §3.4），右鍵/Mac 的 contextual menu 是即時觸發。兩者要開放同一組
動作選單，不要讓某個平台獨占某個操作——手機上長按能做的事，桌面版右鍵也該做
得到，反之亦然。

**精度需求不同。** 滑鼠/軌跡板允許像素級選取，觸控目標必須更大、容錯更高。
Mac Catalyst 的 pinch/rotate 手勢會自動轉換成指標事件而不是逐點觸控——換句話
說，同一組手勢語意換了輸入方式後，行為要對應，而不是重新發明一套。

## 2. 單一焦點 vs 多視窗

iPhone 的心智模型是「一次一件事」：即使系統支援多工（PiP、切換 App），主線互
動假設仍是單一堆疊、單一返回路徑往回退。iPad/macOS 允許並行：視窗分「primary
（主要導航與內容）」和「auxiliary（單一任務、完成即關）」兩種，macOS 視窗還有
main / key / inactive 三種狀態，前景與背景視窗的視覺差異（標題列色彩、陰影）是
用戶判斷「現在誰在接受輸入」的唯一依據。

**桌面網頁版本身已經是瀏覽器裡的一個視窗**，不需要再自造一層視窗殼或假的視窗
控制項——HIG 明講：自製 window UI 除非完美複刻系統外觀與行為，否則會讓 App
「看起來壞掉」。這條原則直接對應 `DESIGN.md` §3.1 的玻璃 header/footer 規則：
浮層要用透明穿透而不是寫死一層假的系統列。

**桌面導航不要機械複製手機的 tab bar。** Mac Catalyst 指出，iPad 的 tab bar
移植到 Mac 更適合改成 sidebar（split view），因為桌面用戶習慣一次看到完整層
級，而不是逐層點進去。desktop 與 mobile 各自的導航形態應該分別設計，但要共用
同一組資訊架構——這也是 `DESIGN.md` §5.4「桌面/手機改同一功能要同一 agent
一起做」的理由所在。

## 3. 系統手勢與返回：哪些不能覆寫

iOS 的側滑返回、下拉關閉、Home Indicator 手勢是系統保留動作，App 不能在同一
手勢區定義衝突的操作。狀態列預設透明、內容可能透出來，但**不能讓用戶誤以為狀
態列後面的東西是可以點的**——HIG 原文明講「don't imply that content behind it
is interactive」。這正是 `env(safe-area-inset-*)` 存在的原因：系統保留區（狀
態列、Home Indicator）不能被我們的浮層當普通版面疊加可互動元件，也不能整塊遮
住讓用戶連時間、訊號都看不到。

如果因為沉浸式體驗（例如全螢幕看圖）暫時隱藏系統列，一定要留一個輕觸就能恢復
的手勢——**永久藏起來，等於逼用戶離開 App 才能看時間**，這是明確禁止的行為。

## 4. 中斷與恢復：App 隨時可能被切走

Multitasking 的核心假設是「你永遠不知道用戶什麼時候會切走」，所以任何進行中
的狀態都要能隨時存檔、隨時還原，不能依賴用戶自己記得自己在哪。需要人持續注意
力的動作（播放中的語音、輸入中的訊息、進行中的動畫）在切走時要暫停，切回來要
無縫接續，不能讓用戶錯過內容或被迫從頭開始。

用戶主動發起的背景任務（上傳、生成、下載）要在背景完成，不能因為分頁被切走或
App 進背景就砍掉重來。通知要克制：只有重要或時間敏感的任務完成才推播，常規任
務讓用戶自己回來看——這條「分級」思路同樣適用於 LunaTalk 的訊息到達提示音：主
要音訊（正在播放的語音）中斷要整段暫停，次要提示音只需要短暫降低音量、結束後
恢復，不是每次都搶佔。

## 5. PWA 與原生 App 沒有「重新整理」

HIG 對 launching 的要求很明確：**App 重啟後要恢復先前狀態，不要讓人重走一
遍**，而且要恢復到很細節的程度——scroll 位置、視窗狀態、正在編輯的內容，都算
數。這條要求展開成推論鏈，是這份文件被建立的直接原因：

- **原生 App、已安裝的 PWA，沒有「網址列旁邊的重新整理按鈕」這個逃生口。** 用
  戶能做的只有把 App 切到背景再切回來，或直接砍掉重開。如果我們的錯誤修復手
  段預設「使用者會重新整理頁面」，這條路徑在這兩種形態下根本不存在——等於一
  條死路，用戶會卡在那裡，沒有任何自救動作可做。
- **即使在有網址列的純網頁（H5）形態下，「叫用戶重新整理」也不是修復，只是把
  我們沒做狀態恢復的責任轉嫁給使用者。** 而且同一個邏輯漏洞一旦被複製到
  PWA/App 形態，後果從「用戶多按一下」變成「用戶真的卡住、無路可退」。
- **正確做法分兩層：**
  1. **自己恢復優先。** 重連、重試、輪詢、從本地或伺服器狀態重建——只要邏輯
     上做得到，就不該讓使用者介入。
  2. **真的需要使用者動作時，給一個他在當前畫面按得到的按鈕。** 例如「重新
     載入這則訊息」「重試」，按鈕必須就在當前情境內，不能要求使用者離開當前
     畫面（關掉 App、清快取、重新整理整個頁面）才能繼續。

這條 HIG 依据是既有產品邊界（見 memory
`chat-stuck-no-dead-end-boundary`：I-1 五分鐘內必須有結果、I-2 停止永遠可
用）在「App 生命週期層」的對應版本——同一個「不能卡死」的產品承諾，從「對話操
作」延伸到「App 本身的啟動與恢復」。

**具體檢查：** 任何 error state / empty state / 卡住狀態的文案裡出現「請重新
整理」「請重新打開 App」「請重新登入再試一次」，先問能不能自己恢復；如果真的
不能，有沒有給一個畫面內、不需要離開情境就能按到的按鈕。這條規則同時受
`.claude/rules/user-facing-message.md` 約束——就算按鈕文案要引導使用者手動重
試，也不能用「reload」「刷新」這類術語，要用使用者看得懂的動作詞。

## 6. 系統入口決定第一眼該顯示什麼

Launching 對啟動畫面的要求：**它只是「讓人覺得快」的過渡，不是品牌宣傳**，設
計上要跟第一屏幾乎一模一樣，不能帶文字（未在地化的文字閃一下最刺眼），也不能
放 logo 或宣傳語，否則等於自己製造了一次「畫面跳動」。LunaTalk 的啟動 loading
頁同理：越安靜、越像最終畫面越好，不要塞進會閃一下才消失的裝飾。

系統層的快速入口（長按 icon 的 Home Screen quick action、Siri/Spotlight 捷
徑）共用同一條原則：**直達任務，不必先開 App 首頁**。這條原則直接對應 PWA 的
安裝捷徑、通知點擊、深層連結——點進來要直接落在相關內容（那則對話、那張角色
卡），不是丟回首頁讓人重新找路。Widgets 的互動設計原則也是同一句話：deep link
到跟內容直接相關的位置，不要讓人自己導航過去。

Web view 的規則：如果內嵌網頁只是「臨時看一下、不離開情境」，可以不做前進/
後退；但一旦讓用戶在裡面瀏覽多個頁面，就要提供前進/後退控制。**不要試圖用內
嵌 web view 重造一個瀏覽器**——LunaTalk 的外部連結（例如分享連結、第三方登入）
該交給系統瀏覽器就交給系統瀏覽器，不要為了留住用戶而把 Safari/Chrome 的功能
在 App 裡重做一遍。

## 檢查表

1. 常用操作是否放在手機單手可觸及的中下區域，而不是照搬桌面「頂部工具列」的
   直覺？
2. 有沒有任何資訊只透過 hover 才能取得？觸控裝置上有沒有等價的長按/點擊路徑？
3. 長按與右鍵是否觸發同一組動作？兩者的手勢時機（計時 vs 即時）是否符合各自
   平台慣例？
4. 桌面版是否自製了視窗框、假的視窗控制項？能不能改用瀏覽器原生行為，不去複
   刻系統外觀？
5. 有沒有在同一手勢區覆寫系統保留手勢（側滑返回、下拉關閉）？
6. 浮層或沉浸模式有沒有蓋住、誤導狀態列與 Home Indicator 這類系統保留區？隱藏
   後能不能一個手勢恢復？
7. 使用者切到背景又切回來，正在做的事（輸入中的訊息、播放中的語音、上傳中的
   圖片）是原樣接續，還是被清空、被迫重來？
8. 背景任務（生成回覆、上傳圖片）在使用者離開當前畫面後，還能不能在背景跑
   完，而不是被砍斷？
9. 錯誤或空態文案有沒有出現「請重新整理」「請重開 App」這類要求使用者自救的
   措辭？如果真的需要使用者動作，是否有一個畫面內、不用離開情境就能按到的按
   鈕？
10. **這個設計在 PWA 形態下還成立嗎**——沒有網址列的重新整理鍵、沒有系統瀏覽
    器的返回鍵時，使用者還有路可退嗎？
11. 從通知、捷徑、widget、深層連結進來時，是不是直接落在對應內容，而不是丟回
    首頁？
12. 啟動過渡畫面是不是「安靜」的（不帶文字、不像廣告），跟第一屏幾乎一樣，不
    會讓人看到一次跳動或閃爍？
