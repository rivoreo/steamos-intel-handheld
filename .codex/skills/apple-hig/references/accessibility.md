# 無障礙與包容

蒸餾自 HIG「Accessibility」「Inclusion」「Right-to-Left」「VoiceOver」。這份不是
合規清單，是「怎麼讓更多人真的用得了這個 App」——每一條背後都是某一群人此刻
就打不開、看不清、按不到、聽不懂的真實情境，不是為了過稽核而加的裝飾。

無障礙的介面要滿足三件事：**直覺**（用熟悉一致的互動，不用另外學）、**可感知**
（不靠單一感官管道傳遞資訊）、**可調適**（順著系統設定或個人化設定變化）。

## 不要只用顏色傳達資訊

色盲或色弱的用戶分不清某些顏色組合（紅綠、藍橙尤其常見）。任何用顏色表達狀態
的地方（成功/失敗、在線/離線、可用/不可用），都要**同時**給一個非顏色的線索——
形狀、圖示、文字都行。這不是加強版，是及格線：拿掉顏色之後，資訊還要能被理解。

系統色本身已經內建無障礙變體，會隨著「增強對比」「淺色/深色模式」自動調整；
優先用系統色，勝過自己手調一個看起來差不多的色號。

## 對比與字級要跟著用戶的設定走

字級要能被放大，理想上支援放大到至少 200%，而且不是靠用戶自己去系統設定裡摸
索，是介面本身要能撐住變大後的排版不跑版。用細字重字體時要留意：字重越細，
越需要更大的字級才維持得住可讀性。

對比不是「看起來還行」就過關，是有明確的最低標準（WCAG AA 是常見基準）。如果
預設配色沒有達標，至少在系統開啟「增強對比」時要提供更高對比的版本；深色模式
與淺色模式要**分別**檢查，一邊過關不代表另一邊也過關。

## 減少動態偏好要被尊重

快速移動、閃爍、大幅度的縮放位移動畫，對某些用戶不只是「不喜歡」，是會造成
暈眩甚至誘發癲癇的真實風險。系統有「減少動態」開關，打開後這個 App 的責任是
把自動、重複性的動畫收斂——特別是縮放、位移、景深變化這幾種。與其整組拿掉
動畫，更好的做法是把彈簧效果收緊、把位移類轉場換成淡入淡出、避免對著模糊效果
做動畫進出。

同理，涉及閃光/頻閃的媒體內容要能回應「降低閃光」這類系統設定，不能假設所有
用戶都能承受快速閃爍畫面。

## 觸控目標要大，間距要夠

目標太小不是「不方便」，是有些人根本點不中。除了元件本身的尺寸要達到平台建議
的最小值，元件之間的間距同樣重要——太密的按鈕群會讓人一直點錯鄰居。有邊框的
元件之間抓 12pt 左右的留白，沒有邊框的元件抓 24pt 左右，是站得住的經驗值。

**手勢要有替代方案。** 複雜的多指手勢對很多人來說本來就不好做，常用的操作盡量
用最簡單的手勢；如果某個功能只能靠滑動才能觸發（例如滑掉一個項目），一定要
同時提供一個按鈕做同樣的事，讓用不了那個手勢的人也有路可走。

## VoiceOver 需要的是「有意義」，不是「有標籤」

VoiceOver 讓看不到畫面的人靠語音描述使用介面，它讀出來的內容完全取決於我們給
的替代文字，系統元件的預設標籤通常太籠統，需要換成能表達這個元件在這個 App
裡實際做什麼的描述。

**圖片的替代文字只描述圖片本身傳達的資訊，不要重複附近說明文字已經講過的
內容**——VoiceOver 會依序讀出整個區域，重複的敘述反而增加負擔。純裝飾性、不
承載資訊的圖片，應該直接從朗讀順序裡排除，讓用戶少聽一句沒用的話，這是尊重
他的時間，不是偷懶。

**閱讀順序要跟畫面的邏輯順序一致，元素之間的分組/關聯要明講。** 視覺上靠得近、
對齊在一起，明眼人一眼就懂彼此有關係；VoiceOver 使用者聽到的是逐一唸出的線性
序列，如果沒有明確把圖片跟它的說明文字綁在一起唸，兩者在他耳裡就是無關的兩
段話。

**畫面內容或版面在用戶沒有主動操作的情況下改變時，要通知 VoiceOver。** 否則
用戶腦中對畫面的理解跟實際畫面對不上，等於在他看不到的地方偷偷換了地圖。

**標題要能單獨表達這個畫面在做什麼。** 這是用戶進入一個畫面時第一句聽到的話，
含糊的標題等於進門先迷路。

## 包容性用語

**直接對用戶說「你」，少用「使用者」「玩家」這種第三人稱**——那會讓語氣顯得
疏離。「我們」則保留給指代這個產品或公司本身，不要拿來製造一種「我們跟你」
的親密感，那種語氣在錯誤訊息裡尤其容易顯得像在推卸責任。

**術語與縮寫不先解釋就不要用；口語慣用語能不用就不用**——這類表達通常帶著特
定文化脈絡，翻譯後容易失真甚至帶有原本沒意識到的排他含意。

**避免刻板印象，尤其是「預設家庭長相」「預設職業性別」這類無意識假設。** 描繪
人物時涵蓋不同背景、體型、年齡與能力；需要中性指稱時，用不特定性別的說法，
把「他或她」這種二選一的措辭換成群體名詞或重寫句子結構。真的需要蒐集性別欄位
時（例如法規要求），給出「不願透露」「自訂」之類的選項，不要只有兩個選項。

**用「人在前」的方式描述身心障礙**——先講這個人做了什麼、目標是什麼，需要時
再提及相關狀況，而不是讓一個標籤定義整個人。

## 右到左語言：鏡像是預設，不是全部都要翻

RTL（阿拉伯文、希伯來文等）語境下，介面方向整體鏡像，這通常由系統框架自動
處理。真正需要人工判斷的，是**哪些東西鏡像、哪些東西絕對不能鏡像**：

**該鏡像：**
- 表示「前進/後退」「上一步/下一步」的控制項與圖示，因為方向感跟閱讀方向綁定；
- 進度類控制項（進度條、滑桿）與它們搭配的起訖圖示；
- 代表文字或書寫方向本身的圖示（例如靠左對齊的文字列示意圖）。

**不該鏡像：**
- Logo、品牌標誌、勾勾這類「通用符號」——鏡像會讓人認不出來，甚至有品牌授權
  上的問題；
- 照片、插畫這類寫實圖像——鏡像常常會改變畫面原本的意義；
- 描繪真實世界物件、且該物件本身沒有方向性語意的圖示（時鐘在哪裡看都一樣）；
- 具體數字內部的數字順序（541 不管在哪個語境都是 5-4-1）——但如果數字是用來
  表示「第幾個/進度方向」的序列，順序要跟著控制項方向鏡像，數字本身的寫法不變。

**文字對齊看語言，不是看上下文位置。** 一到兩行的短文字跟著當前介面方向對齊；
三行以上的完整段落要跟著段落自身的語言對齊——RTL 語境裡硬把一段左至右語言的
文字右對齊，反而會讓每行的起始點忽左忽右，更難讀。清單裡的項目要整批統一
對齊方向，不要因為某一項剛好是另一種文字就單獨反過來。

## 認知友善：簡單本身就是無障礙

操作步驟越簡單、手勢越接近系統既有習慣，所有人都受益，不只是認知障礙者。要
特別留意兩個容易被忽略的細節：

**不要用倒數計時自動關閉重要的提示或視窗。** 需要更多時間理解內容、或需要用
輔助技術逐步瀏覽的用戶，可能還沒讀完就被系統關掉了。讓用戶自己按掉，而不是
幫他倒數。

**對難以復原的操作，考慮要求二次確認而不是一次。** 這跟一般「可逆優先於確認」
的原則看似矛盾，但這裡談的是為認知負荷較高的用戶提供的加強版保護，前提仍然
是操作本身確實危險且難以復原——不是把二次確認變成到處都有的預設。

## 檢查表

- [ ] 任何靠顏色表達的狀態，是否都有非顏色的第二個線索（形狀/圖示/文字）？
- [ ] 深色模式與淺色模式的對比是否都分別檢查過？
- [ ] 動畫在「減少動態」開啟時是否收斂了縮放/位移/景深效果？
- [ ] 觸控目標的尺寸與間距是否足夠，手勢是否有非手勢的替代操作？
- [ ] 自訂元件是否都有描述「這裡實際做什麼」的替代文字，而不是沿用系統預設籠統標籤？
- [ ] 裝飾性圖片是否已從朗讀順序中排除？
- [ ] 畫面內容非用戶操作而改變時，是否有通知輔助技術？
- [ ] 文案是否直接稱呼「你」，避免不必要的性別與刻板印象假設？
- [ ] RTL 檢查是否分開處理了「方向性圖示」與「寫實圖像/通用符號/真實物件圖示」，沒有一律鏡像？
- [ ] 是否有任何重要提示用倒數計時自動關閉，需要改成用戶主動關閉？
